# ATUNSE HEALTH × FARAWA # PROTOTYPE SCREEN DESIGN SPECIFICATION **Document Type:** Strict Prototype Design Instructions\ **Product:** Atunse Health Digital Health Platform / EMR\ **Audience:** Product Designer, UX/UI Designer, Prototype Builder, Frontend Engineer\ **Status:** Prototype Build Specification\ **Version:** 1.0\ **Date:** August 2026 ------------------------------------------------------------------------ ## 0. PURPOSE OF THIS DOCUMENT This document is the authoritative design instruction for the Atunse Health prototype. The prototype must demonstrate the product as a **serious production-oriented EMR and digital health operating environment**, not as a generic hospital dashboard, SaaS admin template, or collection of attractive screens. The prototype must communicate five things immediately: 1. **EMR is the centre of the product.** 2. **Protocols are executable workflows, not PDF documents.** 3. **The patient journey is connected from registration through care, billing and follow-up.** 4. **Trust is built into the platform through consent, auditability and chain-of-custody tracking.** 5. **The system works on mobile and can continue selected workflows offline.** The prototype should make the technology feel **compact, robust, configurable and institutionally credible**. Do not build unnecessary feature breadth merely to make the prototype look large. The visual and interaction design should imply that the underlying system is capable of much more than is shown. ------------------------------------------------------------------------ # 1. DESIGN NORTH STAR ## 1.1 Product Positioning The interface should visually position Atunse as: > **A protocol-driven EMR and digital health operating platform.** Not: - a hospital CRM; - a generic clinic management app; - a research dashboard; - a blockchain product; - an AI chatbot product; - a billing system; - a consumer wellness app. Those capabilities exist, but the **EMR is the primary product**. ------------------------------------------------------------------------ ## 1.2 Core Product Narrative Every major screen should reinforce this operating chain: **PATIENT → CONSENT → BOOKING → EMR → PROTOCOL → CARE → BILLING → FOLLOW-UP → GOVERNANCE → INTELLIGENCE** The interface should make these relationships visible without forcing users to understand the architecture. ------------------------------------------------------------------------ # 2. DESIGN PRINCIPLES ## 2.1 Clinical First The patient record must always feel more important than administration. Clinical information receives the strongest visual hierarchy. ------------------------------------------------------------------------ ## 2.2 Action Over Decoration Every dashboard element must answer one of these questions: - What needs attention? - What happened? - What is happening now? - What happens next? - Who is responsible? - Is there a risk? - Is the record complete? Do not add decorative charts simply because the screen looks empty. ------------------------------------------------------------------------ ## 2.3 Dense but Calm Healthcare software needs information density. However, density must come from **structure**, not clutter. Use: - clear grouping; - strong alignment; - restrained cards; - tables where tables are appropriate; - timelines; - status chips; - progressive disclosure. Avoid: - giant rounded cards; - excessive gradients; - excessive shadows; - oversized icons; - decorative illustrations; - excessive whitespace around critical data. ------------------------------------------------------------------------ ## 2.4 One Record, Many Views The same patient data should appear consistently throughout the prototype. If a patient is booked on the Scheduling screen, that appointment must appear in the patient record. If consent is withdrawn, the patient record must show it. If a clinical encounter generates a bill, the financial history must reflect it. If a protocol step is completed, the patient's protocol timeline must reflect it. The prototype must feel like **one connected system**. ------------------------------------------------------------------------ # 3. VISUAL SYSTEM ## 3.1 Overall Aesthetic Use a **premium clinical enterprise aesthetic**. Reference characteristics: - white or very light neutral canvas; - deep navy as the primary brand colour; - restrained heritage-gold accent; - charcoal primary text; - muted slate secondary text; - subtle neutral borders; - minimal shadows; - compact cards; - generous but controlled spacing. No gradients. No neon. No glowing AI effects. No futuristic blockchain imagery. No cartoon medical illustrations. ------------------------------------------------------------------------ ## 3.2 Colour System Use the following base palette: ----------------------------------------------------------------------- Token Value Usage ----------------------- ----------------------- ----------------------- Primary Navy `#002F5F` Primary navigation, headings, primary actions Deep Navy `#003F7D` Hover/active states Heritage Gold `#D4AF37` High-value accent, selected states, trust indicators White `#FFFFFF` Main surface Surface `#F8F8F6` Page/background surfaces Text `#111111` Primary text Secondary Text `#667085` Supporting text Border `#E4E7EC` Dividers and controls Success restrained green Confirmed/completed Warning restrained amber Attention Danger restrained red Critical/problem Info restrained blue Informational ----------------------------------------------------------------------- Do not use colour as the only indicator of status. Always combine colour with text, iconography or shape. ------------------------------------------------------------------------ ## 3.3 Typography Use **Inter** throughout the application. Suggested hierarchy: - Page title: 28--32px / 700 - Section title: 18--22px / 650--700 - Card title: 15--17px / 600 - Body: 14px / 400--500 - Table: 13--14px - Supporting text: 12--13px - Micro labels: 11--12px / 600 Avoid giant dashboard typography. This is a clinical system, not a marketing website. ------------------------------------------------------------------------ # 4. CRITICAL USER FLOWS The prototype must support the following clickable journeys. ## Flow A --- New Patient Login → Dashboard → Register Patient → Consent → Patient Record → Book Appointment → Appointment Confirmation ------------------------------------------------------------------------ ## Flow B --- Existing Patient Dashboard → Patient Search → Patient Record → Timeline → Clinical Encounter → Save / Sign → Billing ------------------------------------------------------------------------ ## Flow C --- Protocol Patient Record → Active Protocol → Session → Eligibility → Consent → Pre-treatment → Administration → Monitoring → Complete → Follow-up ------------------------------------------------------------------------ ## Flow D --- Existing Data Migration Patients → Import / Review → Match Records → Review Exceptions → Confirm → Patient Record → Migration History ------------------------------------------------------------------------ ## Flow E --- Consent Patient Record → Consent → Current Status → View History → Renew / Withdraw → Verification → Audit ------------------------------------------------------------------------ ## Flow F --- Chain of Custody Trust → Chain of Custody → Search Asset → Asset Detail → Custody Timeline → Transfer → Confirm → Ledger Verification ------------------------------------------------------------------------ ## Flow G --- Offline Mobile → Offline → Clinical Workflow → Capture Data → Pending Sync → Reconnect → Synchronise → Conflict Review if necessary ------------------------------------------------------------------------ ## Flow H --- Ogami Ogami → Patient enquiry → Identify / create patient → Availability → Booking → CRM update → Appointment created → Confirmation ------------------------------------------------------------------------ # 44. DESIGNING THE PATIENT RECORD AS THE CENTRE The patient record should be the most polished screen in the prototype. It must demonstrate that all other platform capabilities converge around the patient. For one patient, the prototype should be able to show: **Identity** ↓ **Consent** ↓ **Appointments** ↓ **Clinical encounters** ↓ **Active protocol** ↓ **Billing** ↓ **Communication** ↓ **Documents** ↓ **Audit** This is the screen that should convince a stakeholder that the product is not a collection of disconnected modules. ------------------------------------------------------------------------ # 45. DESIGNING THE PROTOCOL ENGINE AS A DIFFERENTIATOR The protocol engine must be visually distinct from ordinary EMR forms. It should show: - workflow state; - required actions; - responsible role; - timing; - conditions; - exceptions; - approvals; - version; - evidence. A normal form says: > "Enter information." The protocol engine should communicate: > **"This is the authorised workflow. This is where you are. This is > what must happen next. This is who must perform it. This is what > happened."** ------------------------------------------------------------------------ # 46. DESIGNING TRUST WITHOUT BLOCKCHAIN THEATRE Do not use: - chains of glowing blocks; - cryptocurrency symbols; - wallet metaphors; - giant "BLOCKCHAIN" labels; - futuristic circuit graphics. Instead use: **Verified** **Ledger recorded** **Tamper-evident** **Signed** **Actor verified** **Timestamp verified** The technology should be visible through **trust outcomes**, not gimmicks. ------------------------------------------------------------------------ # 47. DESIGNING AI WITHOUT AI THEATRE Do not make AI the visual centre of the platform. AI is an intelligence layer. Use AI where it helps users make decisions. Every AI insight should answer: 1. What was detected? 2. Why does it matter? 3. What evidence supports it? 4. What should the user consider? 5. Can the user accept, reject or investigate it? Always show: **AI-generated · Human review required** where appropriate. ------------------------------------------------------------------------ # 48. DATA VISUALISATION RULES Use charts only where they help decisions. Recommended: - line chart for trends; - bar chart for volumes; - compact progress bars for adherence; - timeline for events; - table for exact operational data. Do not turn every KPI into a chart. Healthcare users need precision. ------------------------------------------------------------------------ # 52. ACCESSIBILITY Minimum requirements for prototype: - readable contrast; - keyboard focus; - clear focus state; - labels on all controls; - no colour-only status; - large mobile touch targets; - meaningful error messages; - logical tab order. Do not use light grey text for important information. ------------------------------------------------------------------------ # 53. SECURITY UX The interface must communicate controlled access without making the product annoying. Examples: Sensitive action: **Authorisation required** Critical record: **Restricted access** Emergency access: **Break-glass access** After use: **Reason required** Do not hide security actions in obscure menus. ------------------------------------------------------------------------ # 54. For protocol: > **No active protocol** Assign an approved protocol to begin a governed > clinical workflow. Review the conflict before continuing. Never use: > Error 500. as the primary user-facing message. ------------------------------------------------------------------------ # 56.
